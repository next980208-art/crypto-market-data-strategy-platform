# 주요 기술적 의사결정

이 문서는 단순한 기술 목록이 아니라 선택 이유, 대안, 비용과 한계를 기록합니다.

## 1. 원천 이벤트를 Kafka에 먼저 보존

**결정:** 실시간 WebSocket 이벤트를 가공하기 전에 Kafka 원천 토픽과 압축 아카이브에 기록합니다.

**이유:** 특성 계산 로직이 바뀌어도 동일 이벤트를 재처리할 수 있고, 장애 시 수집과 처리 단계를 분리해 복구할 수 있기 때문입니다.

**트레이드오프:** 단일 프로세스보다 운영 구성과 저장 비용이 늘어납니다. 이 저장소에서는 개발 환경용 단일 브로커를 사용하므로 다중 브로커 장애 허용성을 주장하지 않습니다.

## 2. 배치와 스트리밍에 동일한 데이터 계약 적용

**결정:** 이벤트 식별자, 시간 단위, 필드 검증과 특성 정의를 두 경로에서 공유하고 동등성 테스트를 둡니다.

**이유:** 연구 시 계산된 값과 실시간 추론 시 계산된 값이 다르면 백테스트 결과를 운영에 재현할 수 없기 때문입니다.

**트레이드오프:** 공통 계약을 변경할 때 배치·스트리밍 코드와 테스트를 함께 갱신해야 합니다. 대신 변경 영향이 명시적으로 드러납니다.

## 3. 무작위 분할 대신 Walk-Forward 검증

**결정:** 시간 순서를 유지한 학습·검증·테스트 구간을 사용하고 정책 선택 이후의 구간은 한 번만 평가합니다.

**이유:** 금융 데이터의 미래 시장 구조가 학습 데이터에 섞이는 누수를 줄이고, 시점별 성능 변화와 비용 민감도를 확인하기 위해서입니다.

**트레이드오프:** 무작위 교차검증보다 사용 가능한 표본과 점수가 줄고 계산 비용이 증가합니다. 하지만 실제 의사결정에 가까운 보수적 평가를 우선했습니다.

## 4. 정확도보다 비용 차감 후 기대값을 우선

**결정:** 분류 정확도만으로 전략을 승인하지 않고 평균 R, 누적 수익률, 최대 낙폭, 거래 수, 주별 지속성을 함께 평가합니다.

**이유:** 방향을 자주 맞혀도 작은 이익과 큰 손실, 수수료와 슬리피지 때문에 실제 성과가 음수가 될 수 있기 때문입니다.

**트레이드오프:** 승인 기준이 엄격해져 배포 가능한 전략이 없을 수 있습니다. 현재 결과가 바로 그 사례이며, 이를 실패가 아닌 안전한 판단으로 기록했습니다.

## 5. 연구와 주문 경로 사이에 명시적 게이트 배치

**결정:** 모델 산출물이 존재해도 품질·비용·지속성 기준과 미래 관찰을 모두 통과하지 않으면 `no_trade`를 유지합니다.

**이유:** 개발 구간의 우연한 성과나 과적합된 규칙이 주문 단계로 자동 전파되는 것을 막기 위해서입니다.

**트레이드오프:** 자동화 수준은 낮아지고 최종 승인을 사람이 검토해야 합니다. 금융 시스템에서는 속도보다 실패 격리를 우선했습니다.

## 6. 전체 데이터 대신 검증 가능한 공개 샘플 제공

**결정:** 공개 저장소에는 1,000개 이벤트와 결과 Parquet, JSON 보고서만 포함합니다.

**이유:** 저장소를 가볍게 유지하면서도 입출력 계약과 실행 흐름을 재현할 수 있게 하기 위해서입니다.

**트레이드오프:** 공개 데모만으로 운영 규모의 처리량을 증명할 수 없습니다. 따라서 README에서는 전체 데이터 규모와 공개 데모 결과를 구분해 표기합니다.

## 미채택 또는 보류한 대안

| 대안 | 보류 이유 |
| --- | --- |
| 높은 정확도의 단일 분류 모델을 바로 배포 | 비용 차감 후 손실과 시간대별 불안정성이 확인됨 |
| 개발 구간 성과를 보고 규칙 재조정 | 미래 관찰의 독립성을 훼손하고 선택 편향을 키움 |
| 실제 거래소 API를 연결한 라이브 주문 | 수익성과 체결 품질이 검증되지 않아 위험 대비 가치가 없음 |
| 모든 원천 데이터와 모델을 Git에 포함 | 저장소 크기, 개인정보·자격 증명 위험, 재검토 비용 증가 |
